## 4. 快取策略三組比較（#642 §4.3）

查閱：OpenAI 官方文件 [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)（2026-11-20）。要點：GPT-5.6 以後最短可快取 1024 token；`prompt_cache_key` 選用；Responses API 的 `usage.input_tokens_details.cached_tokens` 與 `cache_write_tokens`；GPT-6.1 Terra 讀取 0.05 倍、30 分鐘寫入 1.25 倍；`prompt_cache_options.mode = "explicit"` 且不放斷點 = 不快取；`previous_response_id` 的 `instructions` 不會延續。Chat Completions 欄位文件沒說，所以全部走 Responses API。

- 同一批 40 個決策點（兩個事件均勻抽樣，同樣請求內容：看圖加場景上下文），依序（不並行）三組：(a) `none` = explicit 模式不放斷點，加每次不同的前綴 nonce（雙重保證不命中）；(b) `prefix` = 前綴固定、`prompt_cache_key` = 場景雜湊，隱含快取；(c) `state` = `previous_response_id` 接續，只用前 15 個決策點（小樣本），每個事件一條鏈。
- 成本以官方倍率計算（讀取 0.05×、寫入 1.25×）並寫進帳本；「答案同基準」指與主實驗 A 組 K=2 兩次答案之一相同（答案型別、鏡頭、偵測 ID）。

| 策略 | 呼叫 | 輸入 token 平均 | cached_tokens 平均 | 命中率 | cache 寫入 token 平均 | 延遲 p50 s | 延遲 p95 s | USD／決策點 | 答案同基準 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---|
| none | 40 | 7857 | 0 | 0.00 | 0 | 3.91 | 5.09 | 0.0085 | 37／40 |
| prefix | 40 | 7842 | 4585 | 0.58 | 3254 | 3.68 | 5.62 | 0.0049 | 38／40 |
| state | 15 | 27010 | 24314 | 0.90 | 2692 | 4.08 | 5.30 | 0.0050 | 14／15 |

- **答案是否一致：** 不同的決策點逐一列出：A4-1 11.2 秒（基準兩次都是自畫框，三組都選了索引框 D5，三種快取都一樣，所以是模型自己的不穩定，不是快取造成）；B4-1 16.6 秒（只有 none 不同）；B4-1 34.0 秒（none、prefix 不同，基準兩次都是自畫框）。K=2 的基準兩次之間彼此也有不同的決策點，所以 37／40 與 38／40 的差別在模型隨機性內，**沒有證據顯示快取改變答案**，但也沒有做 K 次重複來量化。
- **成本：** 前綴快取 -42%。命中率只有 0.58，因為每次的當下影格（約 4–5 張圖）佔輸入大半，無法快取；前綴（場景上下文與參考裁切）幾乎都命中。
- **延遲：** 三組 p50 3.7–4.1 秒，沒有可靠差別（n = 40，同一個延遲分布）。
- **對話狀態：** 輸入 token 隨輪數累積到 27010（每輪帶整串歷史），命中率 0.90，成本 0.0050 比同 15 點的前綴快取（0.0043）高 16%，沒有優勢，還有歷史變長的問題。建議用前綴快取。
- 限制：單一模型、單一時段、每組一輪；快取命中與保留時間取決於伺服器，不保證重現；`none` 的 nonce 做法與 explicit 模式兩者都沒單獨驗證各自是否獨立足以避免快取（兩者同時用，命中 0）。

## 5. 限制與待補

- n 很小：2 個事件、K = 2、單一模型；規則在這兩個事件上本來就沒有錯人，所以**看不出 Agent 在規則錯時糾正的能力**（H1 的核心）。複雜場景是 W3／W4。
- 兩階段挑鏡頭：第二階段只給前 2 名，B4-1 的第 3 名才是對的（37／40 vs 8／40）。試給前 3 名、或讓 Agent 在看了前 2 台沒找到時再要一台（第三階段），是下一個實驗，這次沒有預先承諾，也沒有重跑調整。
- 兩階段的延遲約 8.5 秒，不適合即時；要即時需要較小模型或先在本地用場景上下文挑鏡頭。
- 場景上下文沒有牆面與遮擋；覆蓋多邊形是無遮擋的平面投影，會高估可見範圍。
- 圖是 DRAFT（`GRAPH_NOT_APPROVED`），Agent 看到核定等級；`CAM_ENTRY` 不在鏡頭圖。
- B 組是「分離看圖貢獻」的控制，提示要求只看文字，大量回答「不在」；不是最佳化過的純文字 Agent。
- 帳本的「每日呼叫上限」把被拒絕的列也算進去（DENIED 2378 列），本實驗為此把自己的上限調高（USD 上限不變）。
- `make_transport` 的 ApiGuard 單次預估固定 9000 token，對話狀態組實際輸入到 27010 token，單次上限檢查用的是預估值，不是實際值；帳本的 `prompt_tokens` 存的是依快取倍率加權後的**計費 token**，不是實際輸入 token 數（實際數字在 LOCAL 答案表的 `usage`）。
