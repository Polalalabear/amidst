# 第五章 結論與建議（初稿，2026-11-10）

> 狀態：初稿。標【待補】的地方要等 WP5 實測或使用者補充後再填。格式依系上「專題書面報告格式」第五章：結論、研究限制、研究成果、研究貢獻、後續研究方向、專題過程導入哪些 AI 工具。

## 5.1 結論

本專題做出一套多鏡頭監控影像的檢索與追蹤系統。使用者以介面上的條件（例如衣服顏色）描述目標，系統依序完成五件事：

- 依條件篩出相關鏡頭（Q1）
- 在影像中找出符合描述的人物（Q2）
- 解析使用者選定的查詢條件（Q3；目前處理的是介面上選好的條件，不是自由輸入的自然語言）
- 判斷每一格畫面是否含有目標（Q4）
- 目標離開畫面時決定切換到哪一台鏡頭（Q5）

系統的每個答案都可以回溯到原始影像、時間與計算過程，並把「直接觀測」、「推論」、「缺漏」、「未知」分開標示，不把推測當成事實。

驗證採用 Blender 建置的受控場景，以 r004 的 A4-1（50 秒）、B4-1（42 秒）兩段情境為基準。系統已通過使用者驗收（驗收 A），量測 B 共 270 次取樣、0 次失敗，端對端瀏覽器測試 347 項檢查全部通過。結果顯示，在受控場景下，以規則為主的追蹤與檢索流程可以穩定運作，並提供可追溯的證據鏈。

## 5.2 研究限制

1. **場景是合成的**：測試影像全部來自 Blender 渲染的受控場景，光線、人物外觀與動作都比真實監控單純，結果不能直接推論到真實環境。
2. **場景數量有限**：真實渲染的場景只有少數幾段，4 人場景只有 2 段，必須用合成干擾補足評估樣本，統計上的代表性有限。
3. **不確認身分、不保證物理正確**：系統只判斷「外觀符合描述」，不確認人物身分；鏡頭之間的走動路徑只是推估，物理上是否真的走得通，系統標示為未知。
4. **外觀特徵單一**：目前主要依賴衣服顏色等外觀條件，遇到顏色相近的干擾者（例如同為紅色系），判斷會變得模糊。
5. **不支援自然語言查詢**：使用者目前只能用介面選擇條件，不能直接輸入一句話描述需求（見 5.5）。
6. **參數不是正式研究參數**：顏色判斷參數是 demo 用的設定（D131-DEMO-HSV-v1），還沒有經過正式的研究核准。
7. **運算資源有限**：本機模型的比較需要借用雲端 GPU（Colab L4），受限於時間與費用，測試規模有限。

## 5.3 研究成果

1. 完成 Q1–Q5 第一版 demo 系統，包括操作介面（工作台），可以回放影像、選擇鏡頭與目標、檢視證據，並有展示模式。
2. 建立兩條可重現的測試流程：r004 基準場景，以及 4 人干擾場景（情境卡 v2.1，路線已依實測牆面幾何通過淨距檢查，最小淨距 0.45 m）。
3. 建立自動化品質關卡：持續整合（CI）、版本與資料雜湊紀錄（provenance）、驗收測試先寫好再實作的流程。
4. 完成 Agent 決策模組的介面與接線（WP1、WP2），可以在規則判斷與模型判斷之間切換，預設關閉，不影響原本的 demo。
5. 規則判斷與 Agent 判斷的比較評估【待補：WP5 實測數據完成後填入】。

## 5.4 研究貢獻

1. **可追溯的監控檢索流程**：每個答案都帶著來源影像、時間、計算版本與雜湊，可以回頭查證，適合需要問責的監控應用。
2. **嚴格的資料隔離**：Ground Truth、渲染器軌跡、可見性與深度等「標準答案」資料完全排除在推論流程之外，避免評估結果因洩漏答案而虛高。
3. **不確定性分開標示**：把觀測、推論、缺漏與未知分開處理，系統不知道時會明確說不知道，不會硬給答案。
4. **可重複的受控評估方法**：用情境卡定義人物路線、顏色與干擾條件，先用穿模與淨距檢查器驗證路線合理再渲染，讓評估場景本身可以檢驗、可以重做。
5. **規則與大型語言模型的比較框架**：在同一套題庫、同一組時間限制下比較規則判斷、本機模型與雲端模型，並記錄成本與延遲【結果待補】。

## 5.5 後續研究方向

1. **真實影像驗證**：把系統套用到真實或半真實的監控影像，檢驗在複雜光線與遮擋下的表現。
2. **更多外觀特徵**：在顏色之外加入體型、配件、步態等特徵，並支援多個條件同時篩選，降低相似干擾者造成的誤判。
3. **加入地圖與牆面幾何**：把實測的牆面與門洞資訊放進推論，讓鏡頭切換的路徑推估更合理。
4. **擴大場景規模**：增加人數、鏡頭數與情境種類，例如多次離開又返回、長時間看不見目標、鏡頭視野重疊時的交接。
5. **非人物目標**：延伸到車輛或物品的追蹤。
6. **自然語言查詢**：讓使用者直接用一句話描述需求，由系統轉成檢索條件。本專題曾做出原型（#480、PR #490），目前暫停，未納入本版成果。

## 5.6 專題過程導入哪些 AI 工具

| AI 工具 | 用途 | 使用方式 |
| --- | --- | --- |
| **Claude Code**（Anthropic；Opus、Sonnet、Haiku） | 專案協調與規劃、前端工作台、介面契約與驗收測試、程式審查、評估工具、文件與實驗紀錄 | 一個主對話負責規劃與決策，每個任務另開工作階段（session）執行。依任務難度分配模型：決策與設計用 Opus，寫程式與審查用 Sonnet，例行雜務用 Haiku，以控制成本 |
| **Codex**（OpenAI） | Blender 場景規劃與渲染、偵測與追蹤後端、相機幾何、場景可行性檢查 | 依 Claude 寫好的契約與驗收測試實作，交件後由 Claude 審查 |
| **Argon**【待補：工具全名】 | Agent 模型轉接器（OpenAI、Ollama）、評估工具鏈（題庫、合成干擾、評分、測試執行程式） | 依 GitHub issue 自行領取任務，交件後由 Claude 審查 |
| **RT-DETR**（物件偵測模型） | 偵測影像中的人物，建立偵測索引 | 系統內的感知模組 |
| **本機大型語言模型**（Ollama，例如 Qwen） | Agent 決策比較組 | 在 Colab Pro 的 NVIDIA L4 上執行，固定模型版本與雜湊 |
| **OpenAI 模型**（astra6、sol6.1、terra6.1） | Agent 決策比較組 | 從 Mac 呼叫 API，總預算 USD 100，分階段核准 |

**導入 AI 工具的心得：**

- **測試當關卡**：每項功能先寫好驗收測試，AI 實作到測試通過才算完成，避免「看起來能跑」但實際不對的情況。
- **分工與交叉審查**：不同 AI 工具負責不同範圍，互相審查程式。例如 Codex 交件後由 Claude 審查，Claude 寫的關卡也會再經過一輪 Claude 審查。
- **人做關鍵決策**：合併程式、刪除資料、渲染、花錢呼叫 API 這類不可逆或有成本的動作，一律由人類確認後才執行。
- **全程留紀錄**：所有決策與工作都同步到 GitHub（決策紀錄見 #93），每個任務都留下「實際產出」紀錄，方便回溯與撰寫報告。
