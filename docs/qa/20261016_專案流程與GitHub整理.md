>

> 1. 用合成遮罩的單元測試通過，涵蓋：底部被遮住、碰到畫面邊緣、4-連通會切開但 8-連通能合併、±1 px 對應的地板位移。

> 3. 在任務 1 的 run 上，誤差不比舊版本差，並列出新舊數字對照。
> 4. 原本的 31 個觀測斷言、fixture、track_ref 都沒有被改。
> 5. 只跑了相關測試，加上 `git diff --check`。
>
> **整體驗收：** 在底部看得見的路線上，綠球應該跟著圓柱走，不會亂跳；在底部被擋住的幀，綠球應該顯示為缺失並附原因，而不是放在錯誤的位置。

> 不需要大規模重構，但有幾個便宜的調整，可以明顯省下查找時間。這次追查綠球花的時間，主要卡在這三處：
>
> 1. **一條流程散在 7 個檔案、3 個套件裡**：`engineering/perception.py`、`geometry/inverse_projection.py`、`workbench/frame_baseline.py`、`blender_motion.py`、`blender_physical_review.py`，再加上前端的 `physical-review.mjs` 和 `scene.mjs`。沒有任何一份文件把它們串起來。

> 3. **文件用行號引用程式**：程式一改，行號就對不上。像審計文件裡標的就是特定 commit 的行號。
>
> 另外，前端 `scene.mjs` 一行塞好幾個敘述，又混了好幾種功能，很難搜尋。
>
> **建議只做這幾件小事：**
> - **加一份一頁的流程地圖**（例如 `docs/engineering/PIPELINE_MAP.md`），列出每個階段對應的檔案與函數、輸入輸出，以及該階段用到的門檻值，並從 AGENTS.md 連過去。效益最大，風險為零。
> - **門檻值集中成具名常數或設定檔**，這可以併進 Codex 任務 2 一起做。
> - **文件改用「檔案 + 函數名」引用**，不用行號。之後新寫的文件照這個規則就好，舊文件不必回頭改。
>
> **現在不要做的：**
> - 搬動檔案或拆分模組；
> - 對 `scene.mjs` 整檔重新排版。
>
> 原因是 Codex 正在同一批檔案上做任務，現在動會造成大量衝突，也會打斷來源追溯紀錄。`scene.mjs` 等以後真的要改它時再順手拆。
>
> **時機：** 流程地圖現在就可以寫，它只是新增一份文件，不會跟任何人衝突。其餘調整等 Codex 的兩個任務合併之後再做。

**使用者的問題**

> 會建議審查程式碼用 explore agent 先看，再轉高階模型嗎，若建議則更新建議分級

**當時的回答**

> 不建議把 Explore agent 當成審查的第一步，分級表維持上一版。理由如下：
>
> 1. **Explore 只負責找程式碼，不做審查。** 它只讀檔案片段，用來回答「某段程式在哪裡」。PR 審查要判斷的是程式邏輯對不對、有沒有符合規格，這需要讀完整的 diff，正好不是 Explore 的強項。
> 2. **PR 審查本來就不需要搜尋。** `git diff` 已經列出所有要看的檔案和行數。先讓 Explore 掃一遍，下一個模型還是得自己讀一次 diff，等於多花一次 token，正確率也不會提高。
> 3. **Explore 給的是摘要。** 下一個模型如果根據摘要判斷，等於拿二手資訊審查，可能漏掉細節，正確率反而下降。
>
> Explore 真正有用的時機比較窄：審查時需要確認 diff **以外**的影響範圍。例如 C3b 改了 bootstrap 的格式，要找出前端有哪些地方會讀它。不過 Sonnet 審查者自己 `grep` 一下通常就夠了，不必另開 Explore。
>
> 因此審查流程維持原提案：
>
> > **Sonnet 讀完整的 diff，並跑測試、`git diff --check`、merge-tree → 只有它回報「不確定」或「阻擋」，或 PR 符合「複雜」標準時，才交給 Opus 複核疑點。**
>
> 真正能省 token 的，是 brief 直接寫明規格條文和要檢查的消費端（例如「K3 的 `defaultSceneId` 會讀 bootstrap」）。這樣審查者不必自己找，比多加一層 Explore 有效。
