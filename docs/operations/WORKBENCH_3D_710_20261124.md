## 範圍第5點：t=1s HUD與NO_SIGHTING

程式根因：舊`core-tracking-view.mjs`的3D HUD只把GAP／LOST分成「盲區」，其餘一律寫「追蹤中」。
`NO_SIGHTING`在`buildCoreTrackingViewModel`中是segmentKind UNKNOWN，因此落入錯誤的else。
本輪把狀態文案集中在共享 `scene3dStateText`：

| 來源 | 顯示 |
| --- | --- |
| response.status = NO_SIGHTING | 目前沒有觀測紀錄 |
| ON_CAMERA | 追蹤中 |
| GAP | 盲區（未見目標） |
| LOST | 目標遺失 |
| PENDING | 目標尚未出現 |
| 其他／缺失 | 追蹤狀態 UNKNOWN |

新panel與原3D HUD都讀共享model的stateText，沒有兩份狀態推測。
Node測試分別直接mount新版前台及原core view，驗t=1s／NO_SIGHTING不寫「追蹤中」。
沒有讀取或修改該截圖／任何影片／GT。

**結論**：正式啟動並非必然讀不到。若從pin所在checkout啟動，資產與three的resolved檔案在該REPO或owned root內，

該目錄通常在clone的REPO與owned package外，read_bytes會被guard拒絕而回403；
若clone自己的local存在但沒assets，則回404。環境覆寫若仍指向外部檔案，也不會自動繞過guard。
不能把#623／#709的clone臨時複製手法當作正式啟動已通過。
