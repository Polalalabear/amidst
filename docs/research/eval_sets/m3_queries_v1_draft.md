- 狀態：**`evaluation_eligible=false`**。使用者逐句審完並在 #93 記錄核准之前，這份題集不算正式評估資料；核准後才能改成 `true`，並另存 `v1`（去掉 `_draft`）。

## 1. 設計

### 1.1 三種事件

沿用 [`yyin_q1q3_wording_v1/README.md`](../handoff/yyin_q1q3_wording_v1/README.md) 的定義和判斷順序：

| 類別 | 事件 | 判斷 |
| --- | --- | --- |
| `E1` | 經過某處 | 連續走過，沒有停下，也沒有進出建築 |
| `E2` | 進出室內外 | 穿過門口，外到內或內到外 |
| `E3` | 停留或折返 | 停下超過約 2 秒，或走到一半轉身往回走 |

一段畫面同時符合兩類時（例如出門後在門口站著），每句只問一個動作，時間窗限在那個動作，並在 `notes` 註明。

### 1.2 配比

每類 20 句，共 60 句：

| 說法 | 每類句數 | 說明 |
| --- | --- | --- |
| `P` 精確地點詞 | 6 | 白牆長走廊、停著的車旁、白色建築的門口、轉角、鏡頭代號（`CAM_W1` 等） |
| `V` 模糊空間詞 | 6 | 外面、裡面、走道上、附近、房間那邊 |
| `T` 時間詞 | 4 | 混用三種寫法：兩個完整時鐘時刻（`下午兩點零分十一秒到兩點零分十六秒`、`14:00:00 到 14:00:08`）、省略「點」的結束時刻（`兩點零分八秒到十一秒`）、相對時間（`開始後大約 26 秒到 28 秒`） |
| `C` 地點加時間 | 2 | |
| `NEG` 負例或應反問 | 2 | 一句「無結果」（藍色上衣，影像裡沒有），一句「應反問」（「剛剛那個地方」「他」「那裡」這類沒有前文可指的說法） |

題族：同一件事的不同說法共用 `family_id`（例如 `E1-F01`）。E1 有 5 個、E2 有 4 個、E3 有 5 個事件題族，共 14 個；另有每類 2 個、共 6 個負例題族。

場景分布：A4-1 38 句、B4-1 20 句、P1 2 句。P1 偏少的理由：P1 兩支影片各 8 秒，畫面只看得到「有人從木門前走過」，沒有進出或停留，所以只能出 E1；P1 也沒有宣告時鐘（`UNKNOWN`），不能出時間句。P1 是 `SYNTHETIC`／`ENGINEERING`，依研究企劃 §D.6 只能判 `SUPPORTED_ENGINEERING_ONLY`，不和 r004 合併。

預期結果：命中 53 句、無結果 3 句、應反問 4 句。

### 1.3 欄位

| 欄位 | 內容 |
| --- | --- |
| `query_id` | `M3-<family_id>-<wording_type><序號>` |
| `family_id` | 題族；`-N01`／`-N02` 是負例 |
| `event_class` | `E1`／`E2`／`E3` |
| `wording_type` | `P`／`V`／`T`／`C`／`NEG` |
| `query_text` | 使用者會說的話 |
| `scene` | 評估時綁定的單一 run（A4-1／B4-1／P1）；句子本身不寫場景 |
| `expected_cameras` | 時間窗內看得到這件事的鏡頭，分號分隔；`NONE`＝沒有 |
| `expected_window_s` | 事件時間窗，從影片開始算的秒數（影片左上角燒入的秒數），`開始-結束`，兩位小數；應反問的句子留空 |
| `expected_outcome` | 命中／無結果／應反問 |
| `confidence` | 確定／不確定（看不清、邊界或判斷可議） |
| `evidence_note` | 哪支影片、哪個時間看到什麼，只描述畫面 |
| `notes` | 地點詞對應、為什麼不確定、和其他題族的重疊 |
| `reviewer_decision` | 留空，給使用者填 `通過`／`修改`／`刪除` |

### 1.4 和系統實際能接受的形式對齊

依 `mainline/q1q5`＠`97030cd` 的 `src/amidst/q1q5/q3_rules.py`、`src/amidst/contracts/q_demo/schemas/q1-request.v1.schema.json` 和 `docs/evaluation/Q1Q3_QUESTION_AUTHORING_GUIDE.md`：

- Q1 的條件只有類別（人、車…）、顏色（只限人）、時間範圍、`camera_ids`、`region_ids`。系統**沒有**「經過」「進出」「停留」這類動作條件，Q1 只回答「哪些鏡頭在這段時間拍到符合條件的人」。所以動作詞只是說法的一部分；評分看 `expected_cameras` 和時間。這是本題集最大的限制，見 §3。
- 所有句子都是找人（`FIND_CAMERAS`）。沒有用到追蹤動詞（跟著、追蹤、去了哪裡），沒有問身分、路線、碰撞。
- 規則文法需要**兩個**時鐘時刻（例如 `兩點零分八秒`、`14:00:08`），否則判為需要反問。相對時間、只寫一個時刻、省略「點」的結束時刻，規則版都解析不了；這正是 D121-C 要比較的用字差異，所以刻意保留。答案欄仍依影像寫「命中」，不因規則版解析不了就改答案。
- 時鐘對應：A4-1 的 0 s＝2026-11-01 14:00:00、B4-1 的 0 s＝14:10:00（Asia/Taipei，#238／D89）。P1 沒有宣告時鐘。
- 沒寫時間的句子，依 D86-2 預設整段 run；D86 的實作尚未驗證。
- 地點詞要對到凍結的 camera／region 目錄；r004 正式 region 目錄是否凍結仍 `UNKNOWN`（研究企劃 §5.10），所以 `P` 句的 region 欄先不計分。

## 2. 抽影格的方法

- 來源：`yyin_q1q3_wording_v1_20261103.zip` 的 `videos/`（11 支，zip SHA-256 `b0821299e0992cc047f4a221d2f35014d0c2826681d3bbeb5036622fc4c7e259`，`VIDEOS.json` SHA-256 `b637dddec51bde4a125a056a5207d7f43843720f1d69e7e60894a9793e237cdf`）。LOCAL，解壓在 scratchpad，用完已刪；zip 本身沒有改。
- 工具：ffmpeg 7.1（venv 的 `imageio_ffmpeg` 內附）。
- 第一輪：A4-1、B4-1 每 1 秒取 1 格（5 fps 影片的第 2 格，時間 x.40 s），P1 每 0.25 秒取 1 格；每支片拼成 5×5 的縮圖表，逐張看，記下每台鏡頭有人的時段。
- 第二輪：在事件開始、結束和停留的地方，取全部影格（A4-1、B4-1 是每 0.2 秒 1 格），確認邊界。加密看的時段：A4-1 EXT_CLEAR 6–10 s、35.6–39.6 s；EXT_CAR 7–11 s、25–29 s、36–40 s；W1 9–13 s、14–22 s、36.6–40.6 s、42–50 s；ENTRY 6–10 s、28–38 s；B4-1 R101_IN 2–6 s、26–30 s；BRANCH 12.6–22.6 s；W2 11–15 s、20.6–24.6 s、29.6–33.6 s。
- 沒加密看的：B4-1 CAM_W1、CAM_WIDE（人很小或只露出局部），這些鏡頭出現的句子標「不確定」。
- 沒有讀 `gt_private/`、劇本、路線、freeze JSON 的事件內容、系統輸出或錄製回應。`VIDEOS.json` 只讀了檔名、場景、鏡頭、fps、片長。

## 3. 限制（報告必須揭露）

- **撰寫者偏誤**：題目由系統開發方（Claude Code）撰寫，用字可能和系統的規則詞表、prompt 太接近，讓兩組看起來都比真實使用者好；也可能反過來，刻意寫出規則解析不了的句子而放大落差。M3 報告必須寫明「題目由開發方撰寫，非獨立使用者」。**使用者逐句審核是唯一的把關**。
- **答案由同一人標註**：時間窗和鏡頭由撰寫者看影像決定，沒有第二位標註者，沒有標註者間一致性數字。
- **動作語意沒有被評分**：Q1 只判斷「有沒有人」。一句問「有人停下來嗎」和一句問「有人走過嗎」，只要時間窗相同，系統的正確輸出就一樣。所以這份題集測的是「不同說法能不能被解析成正確的時間和鏡頭範圍」，不是「系統懂不懂停留或折返」。
- **同一題族內，預期鏡頭可能不同**：只講時間的句子，預期鏡頭是該時段所有看得到人的鏡頭；講了地點的句子，只算那個地點的鏡頭。這是依說法本身應得的答案，不是不一致。
- **沒寫時間的句子**：系統預設整段 run，會把同一場景別的時段也找進來（例如 A4-1 外面的鏡頭在 0–10 s 和 26–38 s 都有人）。評分要先決定：沒寫時間的句子是只比鏡頭，還是也比時間窗。
- **題數不足**：研究企劃 §5.10 要求每類至少 10 個題族、合計 90～120 句；這份是 14 個事件題族、60 句。H1-QW 的不一致題族很可能少於 10，依 §1.6 會判 `INSUFFICIENT`，只能做描述。
- 場景只有一個人物（紅色上衣），沒有車在動。

## 4. 審查方式

1. 用 Excel 或 Numbers 開 CSV（中文正常顯示）。
2. 每列看 `query_text` 是否像真實使用者會說的話，`evidence_note` 是否和你在影片裡看到的一樣（可用 yyin 包的 `題集工具.html` 對秒數）。
3. 在 `reviewer_decision` 填：
   - `通過`：照用。
   - `修改`：在 `notes` 後面加 `｜審查=…` 寫要怎麼改（句子、時間窗、鏡頭或預期結果）。
   - `刪除`：不用這句。
4. 特別請看：
   - 標「不確定」的 11 句（`M3-E1-F04-V1`、`M3-E1-F04-T1`、`M3-E2-F02-P1`、`M3-E2-F02-V1`、`M3-E2-F02-T1`、`M3-E2-F04-V2`、`M3-E2-F04-T1`、`M3-E3-F01-V1`、`M3-E3-F04-P1`、`M3-E3-F04-V1`、`M3-E3-F04-T1`）。
   - 模糊說法的答案：同樣是「裡面」，A4-1（有室外鏡頭）判命中，B4-1（全部室內）判應反問（`M3-E2-F04-V2`）。這條界線是撰寫者的判斷。
   - §3 的「沒寫時間的句子怎麼評分」要先定案。
5. 審完存成 CSV UTF-8，交回後由 Claude 依審查結果產生 `m3_queries_v1.csv`，在 #93 記錄核准，才把 `evaluation_eligible` 改成 `true`。審查前後的 SHA-256 都記錄下來；看過系統結果之後不能再改題（研究企劃 §1.1 事先登錄）。
